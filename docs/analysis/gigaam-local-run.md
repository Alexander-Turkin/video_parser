## Как запустить

```bash
mkdir -p data/transcripts && bash scripts/transcribe_gigaam.sh
```

Запускать из корня репозитория. `mkdir -p` обязателен, если вывод заворачивается в `tee`:
без каталога `tee` падает. Скрипт офлайн — ни сети, ни токенов. Полезные флаги:
`--input`, `--outdir`, `--models "v3_rnnt v3_e2e_rnnt"`, `--device`, `--download-root`,
`--skip-prepare`, `--no-chunks` (`--help` печатает справку).

Что скрипт делает по шагам (по фактическому коду `scripts/transcribe_gigaam.sh`):

1. **Проверяет окружение до начала работы.** Ищет `tools/transcribe.py` (иначе «запускайте
   из корня»), выбирает интерпретатор — `./.venv/bin/python`, иначе `python3`; требует
   `ffmpeg`, `ffprobe`, `shasum`; убеждается, что в интерпретаторе есть пакет `gigaam`
   (через `importlib.util.find_spec`, без импорта — импорт тянул бы torch). `/usr/bin/time`
   не обязателен: без него прогон идёт, а пик RSS берётся из метрик `transcribe.py`.
2. **Проверяет веса.** Для каждой модели — `<download-root>/<модель>.ckpt`, а для `*e2e*`
   и `v1_rnnt` ещё и `<модель>_tokenizer.model`. Нет файла — понятная ошибка до прогона.
3. **Готовит фрагмент**, если входного WAV нет: вызывает `scripts/make_sample.sh`
   (`--skip-prepare` это запрещает). В этом прогоне фрагмент уже лежал на диске.
4. **Печатает блок окружения**, размеры чекпойнтов, размер, длительность и SHA-256 входа.
5. **Строит план нарезки ровно один раз**: `tools/chunker.py --input <wav> --outdir <outdir>`
   → `plan.json` и `chunks/`. Один план на все модели — требование протокола замера
   (раздел 5): на разных чанках сравнение скорости ничего не значит.
6. **Прогоняет модели последовательно**, каждую под `/usr/bin/time -l`:
   `tools/transcribe.py --plan … --model … --out … --device cpu --download-root …`.
   `stderr` целиком уходит в `time.txt` и печатается в лог.
7. **Рендерит выходы**: `tools/outputs.py --transcript … --txt … --srt …`.
8. **Прогоняет проверки таймкодов**: `tools/check_timecodes.py --transcript … --srt …
   --json checks.json`, вывод сохраняется в `checks.txt`.
9. **Собирает `summary.md`** — markdown-таблицу сравнения, причём из файлов на диске
   (`transcript.json`, `checks.json`, `time.txt`), а не из перехваченного вывода.
10. **Печатает статус по моделям и список файлов.** Падение одной модели не обрывает
    вторую: ошибки собираются и печатаются в конце. Код возврата `0` — все модели дали
    выходы и прошли проверки, `1` — хотя бы одна не дала.

Форматы:

* **`checks.json`** — схема `checks/1`, машинный итог проверок; `checks.txt` — тот же итог

## Нарезка

### Решения владельца и почему так

* **Своя нарезка, а не `transcribe_longform()`.** `transcribe()` в gigaam 0.2.0 сравнивает
  длину входа с `LONGFORM_THRESHOLD = 25 * 16000` сэмплов и на более длинном бросает
  `ValueError`. Штатный `transcribe_longform()` тянет `pyannote` и требует `HF_TOKEN`
  плюс доступ к gated-модели `pyannote/segmentation-3.0`
  ([`asr-models.md`](../research/asr-models.md)). Поэтому режем сами — одним проходом
  `ffmpeg silencedetect`, без сети и токенов.
* **Разрез по центрам тишины** — в центре паузы шансы разорвать слово минимальны.
* **Паузы длиннее 2 с выбрасываются целиком.** Решение владельца: так быстрее, а в `.srt`
  на месте длинных пауз будут дыры — осознанный выбор, не дефект.
* **Чанк ≤ 24 с.** Два лимита: `--max-chunk` 22 с — рабочая длина, к которой стремимся;
  `--hard-max-chunk` 24 с — абсолютный предел с запасом к 25 с модели, который не имеет
  права нарушить ни один чанк, в том числе после присоединения короткого хвоста.
* **Порог тишины −35 dB** — из [`example-recordings.md`](example-recordings.md), где с ним
  измерена тишина исходной записи. Минимальная длина тишины здесь 0,4 с, а не 1,0 с, как в
  том замере: там считали «сколько в записи тишины», здесь ищем точки разреза, и короткая
  пауза — тоже годная точка.

Параметры по умолчанию, с которыми шёл прогон (`plan.json`, поле `params`):

| Параметр | Значение |
| --- | --- |
| `noise` | `-35dB` |
| `min_silence` | 0,4 с |
| `max_chunk` | 22,0 с |
| `hard_max_chunk` | 24,0 с |
| `min_chunk` | 8,0 с |
| `drop_pause` | 2,0 с |
| `pad` | 0,1 с |

### Что получилось на этом фрагменте

| Показатель | Значение | Откуда |
| --- | --- | --- |
| Интервалов тишины найдено | **91** | вывод `chunker.py` |
| Чанков | **17** (`chunk_000` … `chunk_016`) | `plan.json` |
| Покрытие (звук, отданный модели) | **249,610 с** из 300,000 с — **83,2 %** | `plan.json` |
| Выброшено | **50,390 с** в **14 интервалах** | `plan.json` |
| Длительность чанка | мин **3,500 с**, макс **21,261 с** | `plan.json` |
| Причины разреза | тишина — 6, граница выброшенной паузы — 10, конец записи — 1 | `plan.json`, `cut_reason` |
| Жёстких разрезов по лимиту | **0** (`cut_reason: hard_max` не встретился) | `plan.json` |

Ни одна секунда не потерялась молча: 249,610 + 50,390 = 300,000 с ровно — это инвариант
плана (`coverage_seconds + dropped_seconds = source_duration`).

Из 14 выброшенных интервалов **12** выброшены по `--drop-pause` (пауза длиннее 2 с), а **2**
— по другой причине: это островки, в которых после отрезания пауз осталось 0,970 с и
0,972 с звука, то есть меньше 1 с, и присоединить их к предыдущему чанку было нельзя.
Самый длинный выброшенный участок — **11,593 с** (`00:00:33.736–00:00:45.329`).

Выброшенные интервалы дали **10 разрывов** в итоговых субтитрах, а не 14: несколько
выброшенных участков идут подряд и сливаются в один разрыв. Все 10 разрывов объяснены
планом — проверка покрытия насчитала 0,000 с необъяснённых пропусков.

## Что замеряем

Только объективное — по [`benchmark-plan.md`](../research/benchmark-plan.md), разделы 5 и 7:

| Что | Как получено |
| --- | --- |
| Время загрузки модели, с | таймер вокруг `gigaam.load_model()` в `tools/transcribe.py` → `metrics.model_load_seconds` |
| Время распознавания, с | таймер вокруг цикла по чанкам → `metrics.transcribe_seconds` |
| ×RT | `audio_seconds / transcribe_seconds` → `metrics.realtime_factor` |
| Пик RSS, ГБ | `maximum resident set size` из `/usr/bin/time -l` (на macOS — в байтах) |
| Проверки таймкодов | `tools/check_timecodes.py`, критерии — раздел 7 |

Косвенно, как признак пунктуации и заглавных, считаются число знаков `.,!?` и доля слов с
заглавной буквы. **Это не метрика качества.**

**WER в этот прогон не входит, потому что эталона нет.** Эталонная расшифровка делается
руками (раздел 3 протокола), её ещё не существует, и считать WER не на чем. Любое число
качества здесь было бы выдуманным, поэтому его тут нет — ни для одной модели.

Оговорка про ×RT. Инструмент считает ×RT от **распознанного аудио** (249,610 с), а раздел 5
протокола определяет кратность как `300 / <время работы>`, то есть от полной длины
фрагмента. Числа в таблице ниже — те, что измерены инструментом; пересчёт по формуле
раздела 5 приведён отдельной строкой под таблицей и помечен как расчёт. Разница ровно в
доле выброшенных пауз.

Чего этот замер не даёт: оба прогона — **холодные** (первый запуск процесса, веса читаются
с диска), «тёплого» второго прогона, который требует раздел 5, не было; поэтому стоимость
загрузки весов видна отдельной колонкой, а не как разница двух прогонов.

## Сравнение `v3_rnnt` и `v3_e2e_rnnt`

### Что было известно до прогона

Из [`asr-models.md`](../research/asr-models.md) (вендорская
[`evaluation.md`](https://github.com/salute-developers/GigaAM/blob/main/evaluation.md),
средний WER по 6 наборам): **8,3 % у `v3_rnnt` против 11,2 % у `v3_e2e_rnnt`** — то есть у
e2e на треть больше ошибок. Платим этим за то, что e2e выдаёт текст сразу с пунктуацией и
заглавными, а WER в вендорской таблице посчитан уже после их удаления. Второму нужен ещё
файл токенизатора. На диске чекпойнты почти одинаковы: 425,71 МиБ против 428,13 МиБ
плюс 249,35 КиБ токенизатора (замерено в этом прогоне).

### Что показал прогон

* **Скорость одинакова.** 6,35 с против 6,30 с на распознавание, 39,30× против 39,62×.
  Разница 0,05 с — в пределах шума одиночного прогона, выводить из неё превосходство e2e
  нельзя. Загрузка модели тоже почти не отличается: 1,02 с против 1,14 с.
* **Память одинакова.** 1,76 против 1,77 ГБ пика RSS — разница 5,8 МБ, то есть ~0,3 %.
  Лишний токенизатор в памяти практически ничего не стоит.
* **Пунктуация подтвердилась, и это главное фактическое различие.** У `v3_rnnt` — **0**
  знаков `.,!?` и **0,0 %** слов с заглавной: сплошной поток строчными, как и ожидалось. У
  `v3_e2e_rnnt` — **117** знаков `.,!?` и **12,5 %** слов с заглавной. Отсюда и больше
  символов при меньшем числе слов: 2686 против 2536 при 444 словах против 448.
* **Структура выходов чуть лучше у e2e.** Кадров в `.srt` меньше (84 против 89), а
  суммарная их длительность больше (173,621 с против 151,496 с): пунктуация даёт
  `outputs.py` больше осмысленных точек разбиения, кадры выходят крупнее.
* **По допуску раздела 7 они неотличимы:** 9 из 9 у обеих.

**Чего прогон не показал.** Какая из моделей точнее — этого здесь нет и быть не может: WER
не считался. Разница 8,3 против 11,2 остаётся вендорским числом, на нашей лекции не
проверенным. Решение «e2e или `v3_rnnt` + восстановление пунктуации» принимается после
замера WER на эталоне, а не по этому прогону. Этот прогон отвечает на другой вопрос — обе
модели работают, укладываются в память и скорость с огромным запасом и дают годные
таймкоды.

## Где лежит текст

Расшифровки реальной лекции хранятся **только** в `data/transcripts/` и в git не попадают:
корневой `.gitignore` закрывает весь каталог строкой `/data/`. То же касается нарезанных
чанков, плана, `summary.md` и лога прогона.

**В этом документе нет ни одной строки расшифровки** — только методика, метрики и числа.
Проверить это утверждение можно: все приведённые здесь значения взяты из `metrics`,
`plan.json`, `checks.txt`, `time.txt` и `summary.md`, а из текста — только агрегаты (число
слов, символов, знаков пунктуации, доля слов с заглавной) и один служебный токен «—».

Чтобы перепроверить числа, надо прогнать скрипт у себя: сырые выходы в репозитории
намеренно отсутствуют.
