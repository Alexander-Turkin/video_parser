### Что из этой таблицы следует

**Битрейты пришлось считать по пакетам.** В заголовках потоков `bit_rate` отсутствует
(`n/a` в обеих строках «Битрейт (заголовок)») — типично для WebM от рекордера
видеоконференции. Поэтому скрипт делает один проход `ffprobe -show_entries
packet=stream_index,size` и суммирует фактический объём пакетов по каждому потоку. Это
даёт реальный средний битрейт, а не объявленный.

**Видео — это 69 % файла.** 146,40 МиБ видео против 64,69 МиБ звука; на контейнерные
накладные расходы приходится около 6,5 МиБ (3 %). Отбросив видеопоток, мы сразу убираем
две трети объёма чтения с диска.

**Фиксированного fps у записи нет.** `r_frame_rate = 1000/1` — это не тысяча кадров в
секунду, а служебное значение, которым Matroska помечает поток с переменной частотой
кадров и миллисекундной шкалой времени; `avg_frame_rate` и `nb_frames` контейнер не
хранит. Так пишут рекордеры демонстрации экрана: пока на экране статичный слайд, новые
кадры почти не генерируются, а при смене слайда идёт всплеск. Косвенное подтверждение —
битрейт: 132 кбит/с на разрешении 1536×864 возможны только при очень низкой эффективной
частоте кадров (единицы кадров в секунду). Для пайплайна это не важно, потому что видео
мы не используем; если точное число когда-нибудь понадобится, его считают отдельно:

```bash
ffprobe -v error -select_streams v:0 -count_packets \
  -show_entries stream=nb_read_packets -of default=nw=1:nk=1 \
  -i "vidio_example/Лекция 1 01.09.26 (1).webm"
```

(число пакетов разделить на 9329,651 с).

**Контейнер финализирован корректно.** `format=duration` присутствует и согласуется с
суммой пакетов — признаков оборванной или недописанной записи нет.

## Аудио

### Как измерялось

Один проход декодирования аудио с тремя фильтрами в цепочке — это сильно дешевле трёх
отдельных проходов по 218-мегабайтному файлу:

```bash
ffmpeg -nostdin -hide_banner -nostats -v info \
  -i "vidio_example/Лекция 1 01.09.26 (1).webm" -map 0:a:0 \
  -af "volumedetect,silencedetect=noise=-35dB:d=1.0,ebur128=peak=true" \
  -f null -
```

### Громкость

| Метрика | Значение | Фильтр |
| --- | --- | --- |
| Средняя громкость (RMS) | **−24,1 dB** | `volumedetect` → `mean_volume` |
| Пиковый уровень (sample peak) | **0,0 dB** | `volumedetect` → `max_volume` |
| Интегральная громкость | **−20,1 LUFS** | `ebur128` → `I` |
| Диапазон громкости (LRA) | **9,7 LU** | `ebur128` → `LRA` |
| True peak | **+0,1 dBFS** | `ebur128=peak=true` → `Peak` |

Как это читается:

* **Уровень нормальный.** −20,1 LUFS — тише вещательного стандарта (−23 LUFS для EBU,
  −16 LUFS для подкастов), но это абсолютно рабочий уровень: речь уверенно выше шумового
  порога, крест-фактор (разница между пиком и RMS) около 24 dB — норма для речи.
* **Запись упирается в потолок.** `max_volume = 0,0 dB` и true peak `+0,1 dBFS` означают,
  что отдельные пики достают до полной шкалы и слегка её превышают. Это не повод
  нормализовать: клиппинг, если он есть, уже записан в файл, и нормализацией его не
  убрать. Судя по тому, что средний уровень на 24 dB ниже, это единичные выбросы
  (удары по столу, щелчки микрофона), а не постоянная перегрузка.
* **Динамика ровная.** LRA 9,7 LU — лектор не «уплывает» от микрофона. Компрессия не
  нужна.

### Тишина

Пороги, с которыми получена оценка, — **`noise=-35dB`, минимальная длительность
`d=1.0` с**. Порог выбран так, чтобы фоновый шум и дыхание в микрофон не считались речью,
но и короткие межфразовые паузы не раздували оценку: при `d` меньше секунды в лекции
набегают тысячи интервалов, бесполезных для планирования пайплайна.

| Метрика | Значение |
| --- | --- |
| Интервалов тишины (≥ 1,0 с, ниже −35 dB) | **1103** |
| Суммарная длительность тишины | **00:31:59.116** (1919,116 с) |
| Доля тишины от записи | **20,6 %** |
| Полезной речи (оценка) | ≈ 02:03:30 (7410,5 с) |
| Самые длинные паузы, с | 16,49 · 14,72 · 11,79 · 10,46 · 8,48 |

Что это значит:

* Пауза длиннее секунды случается в среднем **раз в 8,5 секунды** — обычный ритм живой
  лекции с объяснением по слайдам, а не запись с провалами.
* **Длинных мёртвых зон нет.** Самая долгая пауза — 16,5 секунды; перерыва на 5–10 минут
  в записи не было. Это снимает самый острый сценарий галлюцинаций Whisper (модель
  «досочиняет» текст на многоминутной тишине), но не отменяет риска на паузах по 10–16 с.
* Доля тишины 20,6 % — это примерно полчаса, который можно не подавать в модель вовсе,
  если включить VAD-нарезку. Прямая экономия времени распознавания около 20 %.

Оценка чувствительна к порогу; прогнать второй набор для сравнения:

```bash
bash scripts/inspect_media.sh "vidio_example/Лекция 1 01.09.26 (1).webm" \
  --silence-noise -30dB --silence-duration 0.5
```

### Нужна ли нормализация звука

**Нет.** Решение по цифрам, а не на слух:

* Модели семейства Whisper (`faster-whisper`, `whisper.cpp`) внутри сами приводят вход к
  16 кГц моно и считают лог-мел-спектрограмму, устойчивую к постоянному сдвигу уровня.
  Нормализация ради громкости как таковой распознаванию не помогает.
* Критерии, при которых нормализация всё-таки нужна, здесь не сработали: `LRA` = 9,7 LU
  (порог «нужна компрессия» — 12–15 LU), `I` = −20,1 LUFS (порог «слишком тихо» —
  около −30 LUFS). Оба замера в зелёной зоне.
* Пик на 0 dB — аргумент *против* обработки, а не за: нормализация вверх только добавит
  искажений, а вниз ничего не исправит.
* Отдельный аргумент: звук пришёл из видеоконференции (см. раздел «Видео» — запись сделана
  в Яндекс Телемосте). Клиентский стек WebRTC уже прогнал его через автоматическую
  регулировку усиления и шумоподавление. Ровный LRA — как раз след этой обработки.
  Накладывать поверх ещё один слой обработки бессмысленно и вредно.

**Вывод для пайплайна: `loudnorm` не применяем.** Если на будущих записях замеры покажут
`LRA` выше ~15 LU или `I` ниже ~−30 LUFS — добавляем `-af loudnorm=I=-16:TP=-1.5:LRA=11`
при извлечении WAV. Решение принимается по цифрам каждой записи.

| 2 | 00:51:49 | Слайд «Обучение — это спуск в долину ошибки»: график функции потерь |

| 5 | 02:09:34 | Слайд «Косинусная близость — угол как мера смысла» |

### Что на кадрах

**Это запись экрана с демонстрацией слайдов, а не камера.** Все пять кадров —
один и тот же тип изображения: окно десктопного клиента **Яндекс Телемоста** целиком,
снятое как есть (отсюда и разрешение 1536×864 — размер окна, а не камеры).

Внутри окна:

* **Центр — демонстрируемая презентация.** Курс «Технологии нейронных сетей ·
  Магистратура ЧМИ» (подпись в подвале каждого слайда). Единый шаблон: надзаголовок
  капсом, крупный заголовок, слева схема или график, справа панель с текстом. Номера
  слайдов на кадрах — 5, 3, 8, 8, 5, то есть за время лекции презентацию переключали
  несколько раз (несколько файлов или возвраты назад).
* **Сверху — лента из пяти плиток участников.** Живого видео ни на одной нет: только
  аватарки и буквенные заглушки. У всех плиток, кроме активного говорящего, горит иконка
  выключенного микрофона. Активный говорящий (зелёная рамка) на кадрах 2–5 — один и тот
  же участник.
* **Снизу — панель Телемоста.** Счётчик участников меняется: 20 → 25 → 24 → 25 → 24.
  Индикатор «Запись · Компьютер» — запись велась локально на машине ведущего.

**Важная деталь: слайды на кадрах обрезаны снизу.** Правая текстовая панель не помещается
в область демонстрации, нижние строки срезаны. Если из видео когда-нибудь будут тянуть
текст OCR-ом, часть содержимого слайдов в кадр просто не попала.

### Нужен ли видеопоток для MVP

**Нет, не нужен. Первым же шагом пайплайна отбрасываем его флагом `-vn`.**

* MVP проекта — связный текст транскрипта и, в идеале, SRT/VTT с таймкодами. И то и
  другое получается исключительно из аудиодорожки.
* Говорящей головы в кадре нет вообще — камеры у участников выключены. Видео физически
  не содержит ничего, чего нет в звуке, кроме текста слайдов.
* Диаризация и OCR слайдов явно вынесены за рамки MVP, а это единственные задачи, где
  видео дало бы что-то сверх звука.
* Видео — 69 % объёма файла и декодирование VP8 в горячем пути. Отбросив его, мы
  сокращаем читаемый объём втрое.

**Но видео стоит сохранить на будущее.** То, что на экране именно слайды с крупным
печатным текстом, — это задел: вне MVP из них можно вытащить OCR-ом словарь терминов
(«косинусная близость», «локальный минимум», «RAG-система») и подать его в ASR как
подсказку. На терминологии такого курса это как раз то место, где распознавание ошибается
чаще всего. Исходный `.webm` поэтому не удаляем — кадры всегда можно извлечь заново тем же
скриптом.

## Что это значит для пайплайна

### Извлечение аудио

Рекомендованная команда — 16 кГц, моно, 16-битный PCM WAV. Это нативный вход всех
моделей семейства Whisper, так что ресемплинг делается один раз нами, а не моделью на
каждом прогоне:

```bash
ffmpeg -nostdin -hide_banner -v error -y \
  -i "vidio_example/Лекция 1 01.09.26 (1).webm" \
  -vn -map 0:a:0 \
  -ac 1 -ar 16000 -c:a pcm_s16le \
  "build/audio/Лекция 1 01.09.26 (1).wav"
```

Разбор флагов:

| Флаг | Зачем |
| --- | --- |
| `-vn` | отбросить видеопоток — для MVP он не нужен |
| `-map 0:a:0` | взять ровно первую аудиодорожку, не угадывать |
| `-ac 1` | свести в моно: Whisper всё равно работает с моно, а стерео здесь — микс конференции, оба канала практически идентичны |
| `-ar 16000` | частота дискретизации, которую ожидает модель; 48 000 → 16 000 для речи потерь не даёт |
| `-c:a pcm_s16le` | несжатый PCM — никаких потерь на втором кодировании и мгновенный seek |
| `-nostdin` | чтобы ffmpeg не съел stdin, если его вызывают из скрипта |
| `-v error` | в stdout/stderr только настоящие ошибки |

Фильтры громкости в команду намеренно не добавлены — обоснование в разделе «Нужна ли
нормализация звука».

### Ожидаемый объём аудио

16 000 отсчётов/с × 2 байта × 1 канал = **32 000 байт/с**.

| Длительность | Объём WAV 16 кГц моно 16 бит |
| --- | --- |
| 1 минута | 1,92 МБ (1,83 МиБ) |
| **1 час** | **115,2 МБ (109,9 МиБ)** |
| 2 часа | 230,4 МБ (219,7 МиБ) |
| 3 часа | 345,6 МБ (329,6 МиБ) |
| **Эта запись (02:35:30)** | **298,5 МБ (284,7 МиБ)** |

Обратите внимание: рабочий WAV этой лекции (284,7 МиБ) **больше исходного `.webm` вместе
с видео** (217,6 МиБ) — несжатый PCM дороже, чем Opus на 58 кбит/с плюс VP8. Для одной
лекции это несущественно, но при пакетной обработке десятка записей промежуточные WAV
надо чистить после прогона, а не копить: десять лекций — это около 3 ГБ временных файлов.

Если место станет проблемой — промежуточный формат можно заменить на FLAC (`-c:a flac`,
примерно вдвое меньше без потерь, читается теми же библиотеками). Для MVP это
преждевременно.

Помнить, что это самый вероятный источник «пустых» или выдуманных сегментов в транскрипте |
| **Перегрузка по пику** | `max_volume` = 0,0 dB, true peak +0,1 dBFS — отдельные пики достают до полной шкалы | Ничего не делать: клиппинг уже в файле. Важно лишь не пытаться «починить» его нормализацией — станет хуже |
| **Обрывы и повреждения контейнера** | У этого файла всё в порядке: `duration` в заголовке есть и сходится с данными пакетов. Но WebM от браузерных рекордеров часто не финализирован — нет длительности, битый хвост | Признак — отсутствие `format=duration` или расхождение с фактическим битрейтом. Скрипт инспекции это покажет, потому что считает битрейт по пакетам, а не по заголовку. Лечится ремуксом: `ffmpeg -i in.webm -c copy out.mkv` |
| **Переменный fps и таймкоды** | Запись VFR (`avg_frame_rate` = N/A). Для извлечения аудио это неважно, но важно для таймкодов SRT, если дыры есть и в аудиодорожке | После извлечения сверять длительность WAV с `format=duration` исходника. Расхождение больше секунды — повод насторожиться и перепроверить синхронизацию |
| **Терминология курса** | Материал плотно терминологический («косинусная близость», «локальный минимум», «RAG», «temperature»); на таких словах ASR ошибается чаще всего | Вне MVP — собрать словарь терминов OCR-ом со слайдов и подавать как `initial_prompt`. В MVP — просто знать, что ошибки будут концентрироваться на терминах, и не делать по ним выводов о качестве модели в целом |
| **Имена файлов** | Пробелы, скобки и кириллица в именах — норма для этого проекта | Везде квотировать пути. Скрипт инспекции это уже делает; то же требование к будущему коду пайплайна |

## Говорящие

**Оценка ниже субъективна и сделана по выборочным фрагментам (пять кадров видеоряда).
Диаризация не проводилась** и в MVP не входит. Использовать эти цифры как основание для
технических решений нельзя.

* **Основной говорящий, по всей видимости, один.** На четырёх кадрах из пяти активным
  говорящим (зелёная рамка в ленте участников) отмечен один и тот же участник — тот же,
  чья подпись висит на области демонстрации экрана.
* **Участников в звонке 20–25**, но на всех кадрах у всех плиток, кроме говорящего, горит
  иконка выключенного микрофона. Из этого следует ожидание: эпизодические вопросы из зала
  возможны, но постоянного многоголосья в записи нет.
* Это **наблюдение по интерфейсу конференции, а не измерение звука**. Реального анализа
  речи не проводилось: индикатор активного говорящего мог просто не успеть переключиться
  в момент снятия кадра.

Рабочее предположение для пайплайна: один основной говорящий плюс редкие реплики. Если
на каком-то этапе диаризация понадобится, её нужно делать инструментом, а не глазами.

## Как прогнать новые записи

Скрипт не привязан к конкретному файлу:

```bash
bash scripts/inspect_media.sh "vidio_example/<новая запись>.webm"
```

Полезные опции:

| Опция | Назначение |
| --- | --- |
| `--silence-noise <порог>` | другой порог тишины, по умолчанию `-35dB` |
| `--silence-duration <сек>` | минимальная длительность паузы, по умолчанию `1.0` |
| `--frames <каталог>` | извлечь кадры в указанный каталог |
| `--frames-count <N>` | сколько кадров извлечь, по умолчанию `5` |
| `--help` | справка |

Скрипт не пишет во временные каталоги без явного `--frames`, не ходит в сеть и ничего не
скачивает. Каталог для кадров задавайте вне репозитория (например, `/tmp/...`), чтобы не
засорять дерево проекта.

Сколько это занимает: оба замера громкости и тишины делаются одним проходом декодирования
аудио, плюс один проход по пакетам для битрейтов. На записи 2,5 часа это несколько минут,
основное время — чтение 218 МиБ с диска.
